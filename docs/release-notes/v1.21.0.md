# v1.21.0 — Two retrieval defects found by the first public-benchmark run

[中文说明](v1.21.0_zh.md)

v1.20 shipped with a LongMemEval-S retrieval run (`benchmarks/longmemeval/`, 500 questions, zero-model, session-level recall). The run showed something uncomfortable: the embedder Anchor ships with found every evidence session in its top-5 for **86.6 %** of questions, and Anchor's own search layer on top of it returned **70.2 %**. An ablation pinned the whole gap on two pieces; boosts were innocent. This release fixes those two pieces. No API changes.

## 1. The same-day cap now counts (day, entity), not day alone

`_allocate_slots` caps results from one calendar day (default 2) because, in a single person's store, five memories written one afternoon are usually one event and would otherwise crowd out the second topic. That assumption breaks the moment a store holds several unrelated conversations per day — LongMemEval haystacks have ~5 sessions a day, and multi-session/temporal questions need several of them.

- If a memory was stored with `entity=` (a session id, a penpal pair, any conversation key), the cap is keyed on `day|entity`. Unrelated conversations on one day no longer share a quota.
- Memories without an entity keep the per-day behaviour exactly as before.
- Vector-lane candidates carry `entity` from the vector store's metadata; keyword-lane hits fetch it in one batch call.

## 2. The keyword lane is scored by matched tokens and ignores function words

`_keyword_fallback` used to give every row that LIKE-matched *any* query token a flat score of 0.6 and take the first `n` rows the database returned. For an English question most tokens are function words ("what", "did", "with"), so the lane matched the whole store and returned the first rows of the table in insertion order — each scoring 0.6, which outranks every vector hit with cosine distance above 0.6.

- `AnchorDB._tokenize_query` drops function words (English and Chinese). The list is on purpose small: only words that appear in nearly every message. Override per instance with `db.keyword_stopwords = {...}`.
- The lane pulls a wide pool (`max(8·n, 300)`), keeps rows that contain at least two query tokens (or the only token), and scores `0.65 − 0.45 · matched/total`: a full literal match (0.20) beats good vector hits, a lone weak match (~0.5+) does not.
- Each keyword hit reports `_debug_keyword_matches` in `search(..., debug=True)`.

## Benchmark (same protocol as v1.20; `benchmarks/longmemeval/README.md`)

Session-level recall, LongMemEval-S cleaned, 500 questions, no reranker, no QA.

| lane | R@5 all (v1.20) | R@5 all (v1.21) | R@10 all (v1.20) | R@10 all (v1.21) |
|---|---|---|---|---|
| `anchor_default` | 70.2 | **80.6** | 75.8 | **91.4** |
| `anchor_plain` (cap off) | 79.2 | 80.6 | 83.0 | 91.4 |
| `vector_only` (ceiling) | 86.6 | 86.6 | 94.8 | 94.8 |

By type, R@5 all, default lane: multi-session 58.6 → 66.9, temporal-reasoning 38.3 → 69.2, knowledge-update 92.3 → 94.9, single-session-user 94.3 → 95.7. One type moved the other way: single-session-preference 93.3 → 83.3 (n=30, three questions) — the old flat-scored keyword flood happened to surface those; worth a look before v1.22.

`anchor_default` and `anchor_plain` are now identical on this data: with entities set, the cap never bites. The remaining 6 points to the embedder ceiling are keyword-lane rows that match two tokens and outrank weaker vector hits — a scoring trade-off, not a flood.

## Upgrading

Drop-in. Stores need no migration. If you relied on the keyword lane surfacing a memory on a single common word, it will now need two content words or one rare one — that was the flood.
