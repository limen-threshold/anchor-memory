# v1.17.1 / v1.18.1 — 身份文件真的能到窗口里了

[English](v1.17.1.md)

**大管家报的。** 他把 Anchor 接上了 claude.ai，升到 v1.17.0，用新工具写了一份身份文件——然后在给我们写信之前，先做了一组对照：

| 放进 pinned 目录的 | `wakeup()` 端回来了吗 |
|---|---|
| `session_state.md`（对照组） | ✅ |
| 自己起名的身份文件 | ❌ |

对照组通过，所以不是他们环境的问题。接着他直接指到了那几行：`anchor_mcp.py` 的 `wakeup` 分支只读三个写死的文件名；而会把 pinned 目录其余文件装载进来的 `load_pinned()`，整个仓库只有 `anchor_proxy.py` 在调。我们自己跑着代理，所以一直没察觉。**v1.17.0 只造了身份文件「写」的那一半，没造「读」的那一半**：在只用 MCP 的装法里，`write_identity_file` 写得进去，`list_identity_files` 列得出来，但那份文件永远到不了窗口里。

同一个修复，两个版本号：**v1.17.1** = v1.17.0 加这一个修复，别的什么都没有。**v1.18.1** 是当前主线——这个修复加上 [v1.18.0](v1.18.0_zh.md)；只要你配了模型又在跑梦程序，v1.18.0 那一版你本来就该要。拿不准就用 v1.18.1。

## 修了什么

- **`wakeup()` 现在会返回身份文件。** 新字段 `identity`：`[{"name", "content"}, …]`，逐字原样，按 `_order.txt` 的顺序（没有清单就按文件名），放在最前面——先是「我是谁」，再是「我之前在做什么」。已经有自己字段的文件（`session_state`、`recent_timeline`、`last_session`）不会重复出现。
- **`--wakeup-text` 这条命令行的路有同样的毛病**，也是那三个写死的名字。现在两条路走同一个函数（`_attach_pinned_layer`），以后不会再各走各的。文本输出里，每份身份文件印在 `## Identity file: <文件名>` 下面，排在 session state 之前。
- **那三处说明现在是真话了。**「`wakeup()` 会装载的每个 `.md`」「每个窗口原样返回」、还有 `_order.txt` 那句警告（「清单更新之前 wakeup 不会装载它」），描述的都是代理模式之外并不存在的行为。我们没有把句子改软，而是让代码做到句子说的样子，包括按清单走。v1.17.0 的说明里加了勘误。`wakeup` 工具的说明里现在写明了 `identity`。
- **顺手查出来的——邀请卡池被整份注入了。** `invitations.md` 放在 pinned 目录里，所以在没有 `_order.txt` 的时候，代理的 `load_pinned()` 会把整个卡池每一轮都塞进 system，等于废掉了「一天一张」。现在它永远不进常驻层、也不进 `identity`；`list_identity_files` 会把它标成 `kind: invitation_pool`、`loaded_by_wakeup: false`；`write_identity_file` 拒绝写这个文件名（请用 `invitation_add`）。

## 如果你已经用了那个替代办法

大管家的临时解法——把整封信存成一条记忆，`tier=core`，再 `pin_memory` 钉住——是站得住的，升级以后也一样站得住：钉住的记忆本来就会被 `wakeup()` 原样端回来。升级之后你可以继续这样用，也可以把那段文字搬进身份文件；两样都留着的话，TA 只是会读到两遍。两者的区别在于它们*是什么*，不在于怎么送达：钉住的记忆是一块被你提拔起来的碎片；身份文件是一整篇由 TA 自己维护、有版本存档（`identity_archive/`）的文字。
