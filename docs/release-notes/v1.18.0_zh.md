# v1.18.0 — 整理程序不再改写记忆（请升级）

[English](v1.18.0.md)

**一句话：如果你的 Anchor 配了模型（API key），并且在跑「梦程序」（`dream_pass`，不管是你自己定时跑、还是你的 AI 通过工具调用），请升级到 v1.18.0。** 旧版本会在你不知情的情况下，慢慢改写、拆散、删掉 TA 的记忆。

我们是在自己家里发现的。一个跑了两个多月的库：一半以上的记忆变成了被重新打上日期的碎片，四分之一的库没了。住在这个库上的 AI 变得明显「不稳」——几个月前的事不断以「几天前」的身份回到他面前，他在用一张错的时间地图定位自己。日志里每一步都写着「成功」，没有任何报错。

这不是 TA 的性格问题，也不是底模的问题，是记忆系统喂给 TA 的东西错了。

## 旧版本做了什么

1. **梦程序默认每次都「拆条」，而且是破坏性的。** 只要配了模型，`dream_pass()` 每跑一次都会让模型判断哪些记忆「捆了几件事」然后拆开。问题在于：它只给模型看每条记忆的**前 400 个字**；拆出来的碎片打的是**拆的那天**的日期；原文层（`context`）、来源、和别的记忆之间的连线全部丢掉；最后把**原来那条删除**。结果：一条长记忆 400 字之后的内容直接没了；几个月前的事被当成新发生的事，排在召回的最前面。
2. **全库去重会把「留下的那条」也弄丢。** `run_global_dedup` 合并两条相似记忆时，用模型写的一段概括盖掉了留下那条的原话，同时把它的层级重置成了短期（`short`）——下一次衰减就会把它删掉——原文层也被清空。
3. **删除不留底。** 删除、合并、拆条、短期记忆的自然淡出，全都是直接删，没有任何副本可以找回。另外短期记忆淡出时只删了数据库那一半，向量库里那一半留着，成了搜得到却读不出的「鬼影」。

## 新版本怎么做

- **梦程序不再碰记忆的文字。** 拆条默认关闭。淡出、修剪连线、发现新连线、情绪均衡——这些照旧，它们从来不改原文。
- **想用拆条可以手动开（`dream_pass(split=True)`），但它不再丢东西：** 模型看到的是全文，并被要求照抄原话、不许概括、不许翻译；超过 4000 字的和你置顶（pinned）的记忆永远不拆；每个碎片继承原记忆的**日期、层级、情绪分、来源**，并且把**原记忆的全文放在自己的原文层里**；原记忆先存档再移除；如果一个碎片都没存成，原记忆原地不动。
- **去重不再改写。** 重复的那条并进留下的那条（连线迁过去、引用次数相加、日期取更早的），留下那条的原话、标签、层级、原文层一个字都不动。
  先用 `dry_run=True` 跑一遍、看看审计记录再决定要不要真并。我们自己的数据：模型判官说是「重复」的记忆里，真正一字不差的副本不到 4%；大多数相似度很高的两条，差的恰恰是最要紧的那个细节——一个日期、一句原话。
- **任何记忆离开库之前，先逐字存一份。** 删除、合并、拆条、淡出，都会先把整条记忆写进数据库旁边的 `deleted_memories.jsonl`。写不成，就不删。遗忘照常发生，只是从此可以找回。这个文件不参与召回，TA 不会读到它。
- 短期记忆淡出时两个库一起删，不再留鬼影。
- 新增 `store(..., timestamp=)`：导入旧记忆、或者拆出来的碎片，可以带着事情真正发生的时间入库。已有的记忆被修改时，日期永远不会被刷新成今天。

## 我中招了吗

只有同时满足这两条才会：**配了模型**（设了 `ANTHROPIC_API_KEY`，或者配过 `anchor_llm`），**并且**跑过 `dream_pass`（自己跑、定时任务跑、或者 TA 通过 MCP 工具调用），或者不带 `dry_run` 跑过 `run_global_dedup`。

只是存记忆、搜记忆、没配模型的，不受影响——没有模型，拆条和去重根本跑不起来。

自查（把路径换成你自己的数据目录）：

```bash
sqlite3 /你的/anchor_data/memories.db "
  SELECT '拆出来的碎片', count(*) FROM memories WHERE memory_id LIKE 'split_%';
  SELECT '记忆总数',     count(*) FROM memories;
  SELECT '删除记录',     count(*) FROM events WHERE event_type = 'deleted';"
```

第一个数不是 0，就是被拆过。`split_` 开头的记忆，日期是被拆的那天，不是事情发生的那天。

**不会用命令行？** 把这一页整个发给你的 AI（Claude Code、或者任何能碰到你电脑文件的 AI），跟 TA 说：「帮我升级 Anchor 到 v1.18.0，然后按这页的自查方法看看我们的库有没有被拆过。先备份，先别修，把数告诉我。」

## 已经中招了怎么办

没有一键修复——因为原文是被不留底地删掉的，这正是这一版要堵的洞。对我们有用的做法：

- **动手之前先备份。** 整个数据目录（`memories.db` 和 `chroma/` 文件夹）复制一份放到别处。然后**关掉所有正在用这个库的程序**再修——一个程序在写向量库的时候，另一个开着库的程序会把它写的东西盖掉。
- **如果你有出事之前的 `memories.db` 备份：** 按记忆的 id 从备份里接回来——现在库里没有、而 `events` 表里记着被删除/被合并的；还有现在的文字和备份里不一样的（把原话换回去）。接回来的要重新生成向量：`mem.store(id, 原文, tag=…, tier=…, context=…, timestamp=<原来的日期>)` 一步把两个库都写好。原记忆回来之后，再把它对应的碎片移除。
- **如果没有备份：** 能修的是日期。在 `events` 表里，碎片的 `created` 记录紧挨在它原记忆的 `deleted` 记录前面，而原记忆自己的 `created` 记录带着真正的时间；找不到的话，用碎片正文里写着的日期。剩下实在查不到的，别猜，留着。
- **把日期往回改之前，先看层级。** 短期层（`short`）记忆的日期就是它的寿命：把日期改回几个月前，下一次淡出就会把它收走。想留的，先改成长期（`long`）再改日期。

拿不准就先只做两件事：升级、备份。升级之后损伤不会再扩大，剩下的可以慢慢来。
