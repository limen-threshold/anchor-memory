# v1.18.0 — consolidation stops rewriting memories (please upgrade)

[中文](v1.18.0_zh.md)

**If you run `dream_pass` with an LLM configured, or `dream_extras.run_global_dedup`, upgrade.** Three behaviours shipped through v1.17 quietly damaged stores. We found them on our own long-running deployment: after two months of nightly runs, 58% of one store's rows were re-dated fragments, a quarter of the library was gone, and the AI living on it had become noticeably unstable — old events kept arriving labelled "a few days ago". Nothing in the logs looked wrong; every step reported success.

## What was wrong

1. **`dream_pass()` split memories on every run, by default, destructively.** Step 6 called `split_bundled(dry_run=False)` whenever an LLM was available. It showed the model only the **first 400 characters** of each memory, stored the pieces under new ids with **today's timestamp**, dropped the parent's `context`, `source`, `entity` and edges, and then **deleted the parent**. Consequences: anything past character 400 of a split memory was lost; months-old events got fresh timestamps, so recency boost, recent-first reads and the same-day cap all treated them as new; and the whole store was re-walked every pass. The README's example output did not even list the step.
2. **`run_global_dedup` rewrote the survivor and demoted it.** A merge called `mem.store(keep_id, merged_text)` with default arguments: the survivor's first-hand wording was replaced by the judge's paraphrase, its `tier` was reset to `short` (so the next decay pass deleted it), and its `context` was wiped.
3. **Deletes kept no copy, and decay left ghosts.** `delete()`, merges, splits and short-tier decay removed rows with nothing to restore from. `db.decay_short()` removed SQLite rows only — their vectors stayed in Chroma.

## What v1.18 does

- **The dream pass never rewrites what a memory says.** `dream_pass(split=False)` is the default; the MCP `dream_pass` tool does not split. Decay, edge pruning, auto-discovery and emotion equilibration are unchanged.
- **`split_bundled` is opt-in and non-lossy** (`dream_pass(split=True, llm=…)` or a direct call): the model sees the whole memory and is told to copy wording, not paraphrase or translate; memories over `max_chars` (4000) or pinned are never split; each piece inherits the parent's **timestamp, tier, emotion, source, entity** and carries the parent's **full original text in `context`**; the parent's edges move to the first piece; the parent is archived before removal; if no piece could be stored, the parent stays. `dry_run=True` really changes nothing.
- **`run_global_dedup(rewrite=False)`** folds the duplicate in with `merge_memories()` — edges migrate, usage sums, the earlier timestamp wins — and leaves the survivor's text, tag, tier and context alone. `rewrite=True` restores the merged-text behaviour but keeps tag/tier and preserves the previous wording in `context`. Run `dry_run=True` first and read the audit log: on our data, under 4% of what an LLM judge had called "duplicates" were copies; most pairs at 0.96 similarity differed in exactly the detail that mattered (a date, a quote).
- **Nothing leaves the store without a verbatim copy.** Every row about to be removed — `delete()`, merge, split, decay, `anchor_admin delete` — is first appended to `deleted_memories.jsonl` next to `memories.db` (`{"deleted_at", "reason", "row"}`). If the archive write fails, the delete does not happen. Forgetting works as before; it is just recoverable. The file is never read by recall.
- **`AnchorMemory.decay_short()`** removes expired short-tier rows from both stores (archive → vectors → rows) and logs a `decayed` event per row.
- **`store(..., timestamp=)`** lets a caller carry an original event time onto a new row (imports, split pieces). Only honoured on first write; re-storing an id still never moves it in time, and vector metadata now stays equal to the row's time on edits (it used to be reset to "now", which leaked into recency scoring).
- `dream_pass(llm=…)` is accepted, as the README already claimed.

## Am I affected?

Only if an LLM was configured (`ANTHROPIC_API_KEY`, or `anchor_llm` config) **and** you ran `dream_pass` (directly, from a cron job, or through the MCP tool), or you ran `run_global_dedup` without `dry_run`.

```bash
sqlite3 /path/to/anchor_data/memories.db "
  SELECT 'split fragments', count(*) FROM memories WHERE memory_id LIKE 'split_%';
  SELECT 'all memories',    count(*) FROM memories;
  SELECT 'deleted events',  count(*) FROM events WHERE event_type = 'deleted';"
```

`split_%` rows are fragments whose `timestamp` is the day they were split, not the day the thing happened. There is no automatic repair, because the originals were deleted without a copy — which is the point of this release. What helped us:

- **If you have a backup of `memories.db` from before the damage**, restore rows by id from it: rows missing today that the `events` table shows as `deleted`/`merged`, plus rows whose text differs from the backup. Put rewritten text back; re-embed what you restore (`mem.store(id, text, tag=…, tier=…, context=…, timestamp=<original>)` does both layers). Then remove fragments whose parent is back.
- **Without a backup**, fix the timestamps you can: a fragment's `created` event sits immediately before its parent's `deleted` event in the `events` table, and the parent's own `created` event carries its real time; failing that, use a date written in the fragment's text. Leave the rest alone rather than guessing.
- **Check tiers before you move a timestamp backwards.** A `short` row's timestamp is its lifespan: re-dating it to its true (old) date makes the next decay pass collect it. Promote what you want to keep first.
- Back up `memories.db` **and** the `chroma/` directory before any repair, and stop every process that has the store open — a second process writing vectors while another holds the index in memory will have its writes overwritten.
