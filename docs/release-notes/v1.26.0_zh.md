# v1.26.0 — 关键词车道的 FTS5 预筛、搜索的批量读数、代理的三处补漏

2026-11-16。接口不动；升级 `git pull` 即可。第一次用新版打开旧库会自动建一张 `memories_fts` 表并把已有记忆的分词灌进去（五万条几秒钟）。

这是 v1.25 那次外审剩下的几条——上一版写在「没改的」里，这一版做掉。

## 1. 关键词车道：先问 FTS5 要候选，再跑原来的 LIKE 排序

v1.25 把关键词车道改成「先按命中数排序再截断」之后，每个查询词都要把整张表扫一遍（排序前不能截）。现在多了一张 FTS5 虚表 `memories_fts`，存的是**同一个分词器**（装了 jieba 就用 jieba）切出来的小写 token。查询时先用每个词的前缀匹配向它要一批候选 id（最多 `max(limit×4, 1200)`），原来的 LIKE + ORDER BY 查询只在这批行上跑。**FTS 一条都没命中时，退回整表扫描，和 v1.25 完全一样**。

- 写入时维护：`insert`（含重存同一 id 的 UPSERT）、`delete`、批量衰退删除都同步更新 FTS 行。
- 行为差异只有一处：英文词中间的子串（查 `hose` 命中 `firehose`）FTS 看不见；中文词组两边用同一个分词器切，看得见。
- 关掉：环境变量 `ANCHOR_KEYWORD_FTS=0`，回到纯 LIKE。FTS5 编译不进 SQLite 的环境自动退回并在 stderr 说一句。

## 2. 搜索里的 SQLite 连接风暴

一次 `search()` 以前对每个候选各开两个连接查 `usage_count` 和 `emotion_score`，选中的每条再各开一次 `cite`、一次 `get_context`。现在：

- `stats_for(ids)` 一条 `IN` 查询拿齐所有候选的两个数；
- `cite_batch(ids)` 一条 UPDATE 加完所有选中条的引用；
- `contexts_for(ids)` 一条查询取回全部 context；
- `_ensure_context_column` 每个 AnchorDB 实例只探一次 schema（以前每次 insert / get_context 都探）。

老的单条方法都还在，外部调用不受影响。

## 3. 代理：最后一条用户消息里的图片不再丢

代理往最后一条用户消息前面塞 `<context_now>` 时，把 list-of-parts 形式的 content 压成了纯文本，图片、文件部分全没了——走代理的多模态前端等于静默变成纯文本。现在文本部分合并成一个 text part 放最前面，其余 part 原样保留。

## 4. 代理：模型调用和检索挪出事件循环

`build_turn`（意图切分的模型调用、向量编码、SQLite 读）以前在 async 处理器里同步跑，一个慢的意图切分会让所有并发请求一起等。现在 `await asyncio.to_thread(build_turn, …)`。

## 5. 代理：策展员坏 JSON 不再整轮丢弃

- `parse_json_lenient`：先 `json.loads`，不行就取正文里第一个 `[...]` 或 `{...}`（哪个括号先出现算哪个是外层）。意图切分也用它。
- 策展员输出整体不可用 → 原文落到 `<db>/dead_letter/curator_<时间>.txt`，日志说明；可用但某一条坏（`emotion` 不是数字之类）→ 只跳过那一条，并把它单独落 `curator_entry_*.txt`，其余照存。以前是任何一处异常整轮零存、只 print 一行。

## 没改的

- 分词器仍是 jieba 可选；没装 jieba 时中英都按空白和标点粗切（两边一致，FTS 照样能用，只是中文切得糙）。
- FTS 不做相关度排序，只做候选筛选；排序还是 v1.23 那套（全命中优先，不按时间）。
