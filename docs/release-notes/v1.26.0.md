# v1.26.0 — FTS5 pre-filter for the keyword lane, batched reads in search, three proxy fixes

2026-11-16. No interface changes; upgrade is `git pull`. The first open of an existing store creates one `memories_fts` table and fills it from the existing rows (a few seconds for 50k memories).

These are the items the v1.25 outside review left under "not changed".

## 1. Keyword lane: ask FTS5 for candidates, then run the same LIKE ranking

Since v1.25 the keyword lane ranks by matched-token count before the LIMIT, which means every token scans the whole table. There is now an FTS5 virtual table, `memories_fts`, holding lower-cased tokens produced by **the same segmenter the query side uses** (jieba when installed). A keyword query first asks it for candidate ids (prefix match per token, at most `max(limit×4, 1200)`), and the existing LIKE + ORDER BY query runs only over those rows. **Zero FTS candidates → the full scan runs exactly as in v1.25.**

- Maintained on write: `insert` (including the UPSERT of an existing id), `delete`, and bulk decay deletes update the FTS rows.
- The one behavioural difference: an English substring inside a longer word (`hose` in `firehose`) is invisible to FTS; CJK compounds segment the same on both sides and are found.
- Off switch: `ANCHOR_KEYWORD_FTS=0` returns to plain LIKE. A SQLite built without FTS5 falls back automatically with one line on stderr.

## 2. The SQLite connection storm in search

A single `search()` used to open two connections per candidate (`usage_count`, `emotion_score`), then one `cite` and one `get_context` per chosen row. Now:

- `stats_for(ids)` — one `IN` query for every candidate's two numbers;
- `cite_batch(ids)` — one UPDATE for all chosen rows;
- `contexts_for(ids)` — one query for all contexts;
- `_ensure_context_column` probes the schema once per AnchorDB instance (it probed on every insert / get_context).

The per-id methods still exist; external callers are unaffected.

## 3. Proxy: images in the last user message survive

When the proxy prepended `<context_now>` to the last user message it flattened list-of-parts content to plain text, dropping image and file parts — a multimodal client behind the proxy silently became text-only. The text parts are now merged into one leading text part and every other part is kept as-is.

## 4. Proxy: model calls and retrieval off the event loop

`build_turn` (the intent-split LLM call, the embedding, the SQLite reads) ran synchronously inside the async handler, so one slow split stalled every concurrent request. It now runs under `await asyncio.to_thread(...)`.

## 5. Proxy: malformed curator JSON no longer drops the whole turn

- `parse_json_lenient`: `json.loads`, else the first `[...]` or `{...}` in the text (whichever bracket opens first is the outer container). The intent splitter uses it too.
- Curator output unusable as a whole → the raw text is kept at `<db>/dead_letter/curator_<timestamp>.txt` and the log says so; usable but one entry bad (`emotion` not a number, …) → only that entry is skipped and written to `curator_entry_*.txt`, the rest are stored. Previously any exception anywhere meant zero stores and one print line.

## Not changed

- jieba stays optional; without it both sides split on whitespace and punctuation (consistent, so FTS still works, just coarser for Chinese).
- FTS does no relevance ranking, only candidate selection; ranking is still the v1.23 rule (full matches first, no recency).

## Upgrading

```
git pull
```

Existing stores build and backfill the table on first open; `ANCHOR_KEYWORD_FTS=0` restores v1.25 behaviour at any time.
